# 第四问路由实验（第二轮开发）

仅自建开发样本；没有访问第二轮留出或压力集合，也没有连接官方平台。所有策略只调用 ObservationClient 的公开位置、读数、清除接口。真值仅用于事后评分与单独的路线下界分析。

## 可合入的结论

1. 已发现 16 个不同频道后，停止继续扫未知频道，先清除已知目标。只有 **16 个实际清除成功**才凭上限结束。不要把“已发现 16 个”当作完成。
2. `InformationRoutingMixin` 将未来扫频时间加入路线目标：用离散位置、半径、发射方向先验估计未来每站仍需检测的未知频道数。先验只影响访问顺序，不改变覆盖证书或候选区域。
3. 不推荐固定外环优先、固定内环顺路服务、根据初始读数旋转布局、定位入口成本路线；收益不稳定或变差。定位每拿到一条新方向就回全局调度也只带来很小收益。

主实现见 `routing.py`。`InformationPolicy` 是独立实验类；生产集成可复用 `InformationRoutingMixin`。

记录：`interleave_development_v2_384.json`、`info_development_v2_384.json`、`combo_development_v2_384.json`、`info_ablation_development_v2_384.json`。

部分早期实验通过清空 pending 来停止扫查，导致返回值中 `coverage_complete` 对提前清除16例被高估；**动作、耗时、实际16成功清除和完成证书均不受影响**。实现已改为局部过滤扫描目标，使真实未扫完的覆盖标记保持 false。最终生产基准须重跑，不能照抄早期字段。

## 未采用的路线架构

24例快速筛查（旧开发前24，原始594.02秒/源）全清：延迟服务最佳589.68；固定插入服务610.35；外环先扫626.63；内环先扫601.53；按定位第一探测点建立非对称路线602.77。固定外环早扫省约26次读数，却增加约2559米移动。

初始读数后的布局旋转在旧96：原始551.06（未旋转550.82）；新定位+停扫509.92（未旋转508.60）；新定位+信息成本505.15（未旋转503.19），因此不采用。

## 瓶颈剖析

原始策略新开发384例的平均成本：

| 阶段 | 虚拟秒 | 移动米 | 动作数 |
| --- | ---: | ---: | ---: |
| 发现扫描 | 4750.50 | 15886.71 | 264.13 |
| 定位清除 | 1853.87 | 8557.33 | 28.82 |
| 邻居读数 | 190.78 | 0 | 32 |

约70%时间消耗在发现扫描。使用真值位置和全部25个固定扫描点事后构造的2opt可行路线平均19122.80米；它不是最短路线证明。全部固定扫描点及源周围20米清除圆盘的MST平均17386.95米，是**要求访问全部固定扫描点时**的旅行下界，16源提前停止不适用。详见 `profile_run.py`、`profile_development_v2_384.json`。

新定位+信息成本按源数分层：10源51例平均641.33秒/源、阈值0%；11源64例585.22秒/源、0%；12源59例536.38秒/源、23.7%；13源54例480.56秒/源、74.1%；14源47例457.09秒/源、83.0%；15源55例416.10秒/源、94.5%；16源54例333.74秒/源、94.4%。剩余瓶颈是少源场景的完整覆盖及空频道确认，继续小幅调整服务顺序难以解决。
