# 发现后插入代价代理：开发结果

实现位于 `problem4/experiments_v3/discovery_insertion.py`，未改生产算法。只使用既有公开观测和静态状态先验，不读取真实源。

每次从尚未被已巡检站覆盖的先验状态中取128个。对每条候选路线，先找到假想源首次能收信的巡检站；然后只允许把清除任务插入该站之后的路线段。评分为已知路线移动时间，加预期未发现源的后续插入时间和首次发现前的频道检测时间。中间插入减40米、末端减20米只是光学邻域的代价近似，不作为可行路线或完成证书。

候选包括原路线、反向路线、普通构造，以及至多6个不同首点的路线。固定首点后仅对后缀做2-opt，保留不同巡检方向。定位和全覆盖终止规则不变。

共同基线为21点覆盖加新发现频道共享50米基线。以下为自建development_v2前48例，全部全清：

| 方案 | 平均秒/源 | 400秒通过率 | 平均移动/米 |
| --- | ---: | ---: | ---: |
| 共同基线 | 438.448 | 35.42% | 19523 |
| 插入+发现延迟，源数10–16后验 | 443.115 | 31.25% | 19802 |
| 两项各减半 | 444.593 | 33.33% | 19841 |
| 两项各加倍 | 442.664 | 31.25% | 19850 |
| 使用原独立频道源数后验 | 441.630 | 31.25% | 19741 |
| 仅插入代价 | 441.873 | 31.25% | 19695 |
| 仅发现延迟 | 443.843 | 33.33% | 19795 |

结论：代理目标增加了真实行走，没有净收益，因此未扩大到96/384例，也未进入生产。相比基线约6.1秒的48例程序运行时间，候选约11.3–13.9秒，计算开销可控，主要问题是预测质量。

它把每个未来源的最小插入代价独立相加，忽略未来源间共享路线和未知位置分布的相关性；这些近似可能导致选错，但本轮结果不能单独确认哪项为主因。去掉任意一项也未改善，不能把这个近似目标写成已验证的加速方案。

四项独立测试通过：先发现后服务约束、末端单腿光学余量、首点和全部节点保留、源数期望上下界。结果文件为同目录 `routing_development_v2_48_discovery_base_discovery_discovery_soft_discovery_strong_discovery_legacy_discovery_nolatency_discovery_noinsert.json`。
